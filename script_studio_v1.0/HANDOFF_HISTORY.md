`/api/test-model` 从测试请求或配置取地址和密钥，不读取上述环境变量；它成功不一定证明真实生成会使用相同连接。前端模型下拉框也固定为三个 Gemini 选项，生成总是提交下拉框的值，保存 `default_model` 只更新顶部徽标，不能保证生成模型随配置改变。

## 后端流程与数据契约

### 启动读取

`load_cache(name)` 读取 `data_cache/{name}.json`，缺失时返回空列表。`/api/overview` 读取所有缓存并用主表中的 link 字段统计每个资产的使用次数，按使用次数升序返回前端。

### `/api/slot-machine`

查询参数：`weapon_id`、`rival_id`、`mode`。四种 `mode` 字符串必须保持完全一致：

- `多篇竞对-多向融合`
- `单篇竞对-定向仿写`
- `竞对骨架-原创内容`
- `本体事实-自主原创`

返回对象包含 `material_code`、`weapon`、`gameplay_facts`、`rivals`、`shots`、`components`、`welfare`、`emotions`、以及多篇模式的 `stitched_blueprint` / `stitched_ref_script`。抽样策略是优先选择使用 0 次的资产，否则按 `1/(used_count+1)` 加权；它是概率偏好，不是严格去重。

当前三个参考模式分别抽 3 / 1 / 3 条竞对，但都抽 3 条参考分镜和 5 条组件；单篇模式补齐的分镜可能来自其他竞对。每次随机取至多 2 条关联武器技能和 2 条玩法事实，福利为 1 条。辅助竞对用 `random.choices(k=2)` 有放回抽样，可能重复。即使自主原创也要求竞对缓存非空，是现有入口检查的限制。

### `/api/generate`

请求体由前端把当前抽样组合原样提交，主要字段是 `weapon`、`rivals`、`shots`、`components`、`welfare`、`gameplay_facts`、`stitched_blueprint`、`stitched_ref_script`、`emotions`、`mode`、`rewrite_mode`、`enable_game_profile`、`custom_instruction`、`model`。

后端拼接长 system/user prompt，调用 OpenAI 兼容接口并期望 JSON。随后给每个镜头补 `est_seconds`、`is_over`，并生成 `audit`：`banned_words_found`、`total_chars`、`total_est_seconds`、`total_shot_seconds`、`shot_speed_warnings`、`passed`。当前禁词和玩法对齐不是完整内容审核；前端的“对齐玩法库流程 ✓100%”是固定显示，不是后端计算结果。

输出契约是 `title`、`material_code`、`ref_script`、`full_script`、`hook_analysis`、`body_analysis`、`rhythm_desc`、`dup_summary`、`shots[]`；每个 shot 包含 `shot_num`、`duration`、`ref_text`、`text`、`visual`、`game_action`。输出只按 prompt 请求 JSON，没有严格的结果模型验证。`rewrite_mode` 虽在请求体定义并由前端传入，但后端没有使用它，所以两种仿写选项目前不会产生明确的 prompt 分支。

修改创作规则时保持以下业务边界：我方玩法、武器、强化、福利提供事实；竞对仅提供节奏、句式和创意表达。强化的概率、触发条件、等级和适用武器必须保留；历史文案不是新的事实来源。事实作为后台约束，台词应展现当前操作、反应、压力、选择与结果，避免机械背诵装备系统。现有长 prompt 不等于事实验证器，`audit.passed` 也不代表人工审核通过。

### 草稿与写回

以下旧接口描述为 v1.0 审计，现行写回以本文件顶部和 `feishu_writeback.py` 为准：`/api/writeback-preview` 和 `/api/writeback-draft-preview` 只预览；写回接口统一执行 schema/来源 ID/重复编号/父关联检查、主子批量写入和读回核验。成功必须 `verified=true`；写入收据在 `data_cache/writeback_receipts/`，对超时不确定结果先查编号再恢复，不盲目重建。现行保存保留完整 shots/source_slot，旧扁平草稿仅在原批次可唯一恢复时允许写回。使用 config.json.feishu 的目标配置；同步和缓存加载仍沿用历史逻辑。

- `POST /api/save-draft`：把生成结果按 `material_code` 或 `素材编号` 写入 `data_cache/saved_records/{code}.json`。
- `GET /api/history`：读取该目录下所有 JSON。
- `POST /api/writeback`：把生成结果转换成主表字段，先本地保存，再通过 `lark-cli base +record-upsert --json @临时文件` 写入。
- `POST /api/writeback-draft`：读取草稿 JSON，直接按其中已有字段写回。

重点风险：`/api/writeback` 保存的是字段名为 `素材编号`、`核心卖点`、`二创文案` 的主表形状；`/api/save-draft` 保存的是生成结果形状（`material_code`、`title`、`full_script` 等）。前端已兼容两套字段读取，但新增字段或修复写回前要同时考虑这两种形状。

### `/api/sync`

`sync_feishu_tables()` 对 8 张表逐页调用 `+record-list --limit 200 --offset`，直到 `has_more=false` 或返回不足 200 条，再覆盖写入本地 JSON。它没有生成或更新 manifest 文件，也没有在命令失败时抛出足够详细的表级错误；同步前后应检查缓存数量和 JSON 可读性。

本地快照主要约定：每行 `_record_id` 是飞书记录 ID；关联字段是 `[{"id":"rec..."}]`（代码部分路径也兼容直接 ID 字符串）；选择字段通常是字符串数组。主要关联链为 `skills.所属武器 → weapons`、`rival_shots.关联竞对视频 → rival_struct`、主表的 `关联武器` / `参考竞对` / `参考竞对分镜` / `参考组件` / `关联福利点`。保留这些 ID 和字段类型，不要用名称替代链接。

现有 manifest 来自旧导出目录 `E:\cherry project\project 7\data_cache`，其 `.ndjson` 文件不在当前目录。`main.manifest.json.records_count=116`，实际 `main.json=119`；其余 7 张表数量一致。后端完全不读取 manifest，不能拿它证明当前实时云端 schema。

## 已知问题与优先级

下面是本次分析识别出的候选待办，并非已授权执行的开发计划。当前没有从历史提交或原开发对话确认的进行中任务。

### P0：凭据暴露与配置双轨

`config.json` 含 API Key 和飞书 Base Token，且可由网页直接保存。`server.py` 又有同一套飞书常量。应迁移敏感值到环境变量或本地未提交配置，并让所有运行路径读取同一个配置源。

### P1：真实外部链路未验证

模型生成、飞书同步、写回、读回都缺少当前环境下的端到端证据。处理前要重新确认 `lark-cli` 当前登录身份、授权范围、Base/table 访问和模型服务连通性。

### P1：草稿结构不统一

生成结果草稿和写回字段草稿混用两套命名。建议定义统一的内部数据结构，并在保存/读取/写回边界做显式转换，避免字段丢失。原生“存为本地草稿”只有生成 JSON，无武器/竞对选择信息；草稿直写会把英文生成字段直接提交给飞书，不能当作已完成的可靠补写流程。直接回写只保存整篇字段，不写 `shots[]` 的分镜子记录，回写字段草稿也不保留镜头和 audit。

### P1：同步失败会覆盖有效缓存

当前同步未检查 returncode / `ok`，JSON 解析失败或空数据就退出循环，然后仍 `save_cache`；可能把原缓存覆盖为空数组或半份数据并返回 `ok=true`。CLI 子进程没有 timeout，失败应保留旧缓存并给出逐表状态。

### P1：提示词与实现存在语义漂移

多篇融合蓝图注释写“三段式”，实际返回钩子、排除、高潮、CTA 四段。部分默认示例仍来自竞对游戏。修改时以真实《家园防御战》玩法事实为准，避免把参考竞对机制当我方机制。

### P2：组件匹配过宽

`slot_machine()` 的组件阶段用 `k in 组件类型` 做子串判断，`CT` 可能命中 `CTA`。应改为规范化后的精确枚举匹配，并增加固定样例断言。

### P2：端口与服务管理不一致

README 说可通过配置使用服务，但 `__main__` 固定 8501；`run.bat` 会阻塞并 `pause`。可把 host/port 统一从配置读取，并为开发/生产分别提供明确启动方式。

### P2：前端安全与健壮性

大量 `innerHTML` 直接插入缓存/模型文本，存在 HTML 注入风险；模型配置 API Key 明文回显；没有 favicon；没有前端构建和测试。若部署到多人环境，应先做转义、鉴权和网络访问限制。

### P2：状态绑定和错误提示

重新摇号/切换模式没有清空 `currentGenerated`，可能把旧结果按新组合的关联 ID 写回。打开旧草稿也不恢复其组合，且丢失 `ref_script`、`rhythm_desc` 等字段。后端返回 `saved_locally=true` 时提供 `error`，前端却显示不存在的 `notice`。草稿文件名来自未校验的素材编号或 filename，既可能覆盖同名文件，也可能包含路径，应限制为草稿目录内的安全文件名。

### P2：缓存内容与质检证据

浏览器实际抽到冰红茶的“冰镇2”技能，但缓存描述为“激光的暴击伤害+80%”，提示源数据可能有串项，需回到来源核对；不能仅因关联 ID 正确就认定文本正确。语速计算包含标点且先四舍五入到 0.1 秒才比较；空镜头结果仍可能 `passed=true`。没有真正查重算法，`dup_summary` 是模型输出的摘要。CLI 输出解析失败时直接回写可能仍返回 `ok=true`，草稿回写也没有检查 CLI JSON 中的 `ok`；修复后需读回实际记录。
